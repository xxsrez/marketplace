# Краткая справка о режимах

Применяет `IG-HELP-01`. Читай этот reference только для чистого справочного
запроса о режимах Issue Grinder: он не начинает delivery и не требует загрузки
полного execution protocol.

## Правило ответа

Ответь на языке пользователя и соразмерно вопросу. Для общего запроса назови
пять режимов, default resolver и одно существенное отличие каждого режима. Для
узкого вопроса ответь только о нужных режимах, но не скрывай отличие, которое
может изменить выбор пользователя.

Справочный запрос не разрешает Task Manager scope, не создаёт Goal, не меняет
название Codex task, не обращается к Task Manager и не вызывает subagents либо
Strategic Explainer. Если тот же prompt ещё и явно поручает delivery, кратко
объясни или назови выбранный режим, затем обрабатывай delivery как отдельную
часть запроса по основному workflow.

## Пять режимов

- `Соло` — текущая основная модель последовательно выполняет всю delivery-работу
  Issue Grinder по одному issue или пакету без рабочих субагентов; отдельные
  service/provider agents не считаются исполнителями режима; нужен terminal
  result либо настоящий blocker.
- `Классический` — Sol/controller делает почти всю работу сам; Luna получает
  только тривиальные, строго ограниченные и объективно проверяемые пакеты;
  один независимый Luna reviewer проверяет exact candidate даже на простом
  scope; режим терминальный.
- `Баланс` — основная модель планирует весь scope, сама выполняет критическую
  часть, а до трёх Luna High параллельно реализуют независимые пакеты; затем
  основная модель интегрирует, запускает общие проверки и принимает результат;
  режим терминальный и не имеет штатного отдельного reviewer-а.
- `Менеджер` — Sol/controller один раз планирует весь scope, затем постоянный Luna
  manager ведёт постоянного Luna implementer-а по одной крупной проверяемой
  фазе; после завершения всех фаз один независимый Luna reviewer проверяет exact
  candidate целиком, а Sol/controller проводит final review. Режим терминальный,
  экономит Sol и не создаёт Best-of-N candidates по умолчанию.
- `Экономичный` — Luna выполняет всю содержательную работу и сохраняет один
  проверяемый candidate с независимой Luna-проверкой перед terminal acceptance;
  non-Luna root допустим только как transport/authority оболочка. Это
  единственный режим, который может честно
  остановить текущую попытку на resumable checkpoint без ложного `Done`.

## Режим по умолчанию

`По умолчанию` — не шестой режим и всегда означает `Соло`. `Классический`,
`Баланс`, `Менеджер` и `Экономичный` включаются только явной просьбой
пользователя. Модель, effort, размер scope, число issue, capacity и quota это
правило не меняют. Выбранный режим не меняется внутри непрерывного run без явной
команды пользователя.

## Главное различие Классического и Баланса

В `Классическом` основной исполнитель делает почти всё последовательно, а Luna
получает только точечную простую работу и независимую проверку. В `Балансе`
основная модель тоже остаётся владельцем всей задачи, но параллельно отдаёт до
трёх готовых независимых write-пакетов Luna High и одновременно делает свою
полезную часть. Затем она сама интегрирует, проверяет exact diff и принимает
результат. Это ускоренный Solo-подобный режим, а не экономичный manager loop.

Если пакет нельзя изолировать, проверить локально или отделить от общей
архитектуры, он остаётся у основной модели. Luna handoff не считается общим
результатом без fan-in и integrated checks. Неполный пакет основная модель
сохраняет и заканчивает сама; отдельная цепочка reviewer/reducer не запускается.

## Быстрый выбор

- Нужны ровно текущая модель, последовательная delivery-работа и ноль рабочих
  subagents Issue Grinder — `Соло`.
- Нужна максимальная обычная уверенность без массовых альтернатив —
  `Классический`.
- Нужно ускорить сложную задачу ограниченной параллельной помощью без передачи
  общего управления — `Баланс`.
- Большую связанную задачу нужно провести дешёвым менеджером и исполнителем по
  крупным фазам, а затем независимо проверить целиком — `Менеджер`.
- Проверяющий профиль дефицитен и приемлем честный возобновляемый checkpoint —
  `Экономичный`.

Режим не меняет scope, authority, Production prohibition, Task Manager
lifecycle, требования к evidence или изоляции изменений.
