# Краткая справка о режимах

Применяет `IG-HELP-01`. Читай этот reference только для чистого справочного
запроса о режимах Issue Grinder: он не начинает delivery и не требует загрузки
полного execution protocol.

## Правило ответа

Ответь на языке пользователя и соразмерно вопросу. Для общего запроса назови
пять режимов, default resolver и одно существенное отличие каждого режима. Для
узкого вопроса ответь только о нужных режимах, но не скрывай отличие, которое
может изменить выбор пользователя.

Справочный запрос не разрешает Task Manager scope, не создаёт Goal, не меняет
название Codex task, не обращается к Task Manager и не вызывает subagents либо
Strategic Explainer. Если тот же prompt ещё и явно поручает delivery, кратко
объясни или назови выбранный режим, затем обрабатывай delivery как отдельную
часть запроса по основному workflow.

## Пять режимов

- `Соло` — текущая основная модель последовательно выполняет весь scope по
  одному issue или пакету; subagents нет; нужен terminal result либо настоящий
  blocker.
- `Классический` — Sol/controller делает почти всю работу сам; Luna получает
  только тривиальные, строго ограниченные и объективно проверяемые пакеты;
  режим терминальный.
- `Баланс` — Luna выполняет основную массу ограниченных research,
  implementation, tests и предварительной критики; Sol/controller оставляет
  material decisions, интеграцию и final review; режим терминальный.
- `Рой` — Luna-волны исследуют разные подходы, создают конкурирующие candidates
  и возражения; результат сокращается до одного exact candidate и проходит final
  review; режим терминальный и намеренно допускает больше дешёвых попыток.
- `Экономичный` — Luna выполняет всю содержательную работу и сохраняет один
  проверяемый candidate; non-Luna root допустим только как transport/authority
  оболочка. Это единственный режим, который может честно
  остановить текущую попытку на resumable checkpoint без ложного `Done`.

## Режим по умолчанию

`По умолчанию` — не шестой режим. В начале нового run без явного выбора
top-level модель семейства `gpt-5.6-luna` при любом effort выбирает
`Экономичный`, а любая другая модель — `Классический`. Явный выбор пользователя
сильнее resolver-а; число issue не включает `Соло`; выбранный режим не меняется
внутри непрерывного run без явной команды пользователя.

## Главное различие Классического и Баланса

В `Классическом` основной исполнитель — Sol/controller: он делает почти всё, а
Luna используется точечно только там, где работа действительно тривиальна. В
`Балансе` основной объём лёгкой и средней ограниченной implementation,
research и tests сначала пытается выполнить Luna.

Если в `Балансе` Luna встречает существенную неопределённость, problem/contract
conflict, слабый oracle или задачу сложнее переданного пакета, она не угадывает
и не повторяет ту же попытку. Она сохраняет изменения, checks, evidence и
точную причину остановки и возвращает пакет Sol/controller-у, который решает,
  принять material decision, уточнить contract или сформировать новый безопасный
  Luna-пакет; обычная implementation не переезжает на Sol автоматически.
Final acceptance в обоих режимах остаётся за Sol/controller profile.

## Быстрый выбор

- Нужны ровно текущая модель, последовательная работа и ноль subagents —
  `Соло`.
- Нужна максимальная обычная уверенность без массовых альтернатив —
  `Классический`.
- Нужно экономить проверяющий профиль, сохранив сильный final gate — `Баланс`.
- Полезны альтернативные candidates, широкая критика или поиск сложного решения
  дешёвыми волнами — `Рой`.
- Проверяющий профиль дефицитен и приемлем честный возобновляемый checkpoint —
  `Экономичный`.

Режим не меняет scope, authority, Production prohibition, Task Manager
lifecycle, требования к evidence или изоляции изменений.
